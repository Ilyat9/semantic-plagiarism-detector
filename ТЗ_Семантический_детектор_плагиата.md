# ТЗ: Семантический детектор плагиата и перефразирования (end-to-end ML-проект для портфолио)

**Название проекта:** Semantic Plagiarism & Paraphrase Detection System
**Цель проекта:** веб-сервис, который принимает документ, находит похожие источники в интернете и определяет: (а) прямое заимствование, (б) перефразированное заимствование, (в) вероятный LLM-рерайт. Проект обязан содержать измеримую оценку качества ML-компонента и failure analysis.
**Срок:** 3–4 недели (MVP за 2 недели, ML-прокачка и оформление за 1–2 недели).
**Железо:** MacBook Air M2, 16 ГБ RAM. ML-модели лёгкие (до ~500 МБ) — хватает CPU/Metal. Локальная LLM через **Ollama** для генерации тестовых перефразов.
**Бюджет:** 0 ₽ (поиск через бесплатный `ddgs`, все модели и бенчмарки открыты).

---

## 0. Почему проект структурирован именно так (важно понять до старта)

В 2026 году сама идея «плагиат-чекер на эмбеддингах» не нова — таких репозиториев много. Ценность этого проекта создают три обязательных слоя, которых нет у типовых реализаций:

1. **Evaluation layer** — оценка качества сравнения текстов на открытых бенчмарках (PAWS, STS-B) с таблицей метрик и ablation.
2. **Paraphrase/LLM-rewriting detection** — детекция не только копипаста, но и перефраза.
3. **Failure analysis** — документированный разбор ошибок системы.

Правило проекта: **один ablation (сравнение подходов) ценится больше, чем три новые фичи.** Не расползайтесь по фичам — расползайтесь по качеству оценки.

## 1. Функциональные требования

### 1.1. Базовый контур (по исходному ТЗ DevProjects)
- Веб-страница с загрузкой документа (`.docx`, `.pdf`, `.txt`).
- Извлечение текста из документа.
- Выборка фраз по 5–10 слов, поиск по ним в интернете.
- Скачивание топ-5 результатов поиска по каждой фразе, очистка HTML до основного текста.
- Сравнение документа с каждым источником, итоговый процент схожести.
- Список совпадающих фрагментов + ссылки на источники.
- PDF-отчёт для скачивания.

### 1.2. ML-расширение (обязательная часть этого ТЗ)
- **Двухстадийное сравнение:**
  - Stage 1 — retrieval: би-энкодер (sentence-transformers), косинусное сходство по чанкам. Быстро отсекает нерелевантное.
  - Stage 2 — rerank: кросс-энкодер перепроверяет топ-кандидатов пар «фрагмент документа ↔ фрагмент источника». Точнее, но дороже — потому только на кандидатах.
- **Три типа вердикта по каждому фрагменту:**
  - `verbatim` — прямое копирование (высокое лексическое + семантическое сходство);
  - `paraphrase` — перефраз (высокое семантическое, низкое лексическое сходство);
  - `original` — совпадений нет.
- **Бейзлайн для сравнения:** TF-IDF + косинусное сходство (scikit-learn). Обязателен — без бейзлайна ablation невозможен.
- **Eval-модуль:** скрипт, прогоняющий ваш пайплайн на бенчмарках и выводящий метрики (см. раздел 4).
- **Failure analysis:** минимум 5 задокументированных кейсов ошибок с анализом причин.

### 1.3. Out of scope (осознанно НЕ делаем)
- Пользователи, аккаунты, база истории проверок — это размывает ML-фокус.
- Мультиязычность (только английский; русский — бонусом через `paraphrase-multilingual-*`, но не в MVP).
- Обучение собственной модели с нуля — не нужно, используем предобученные.
- Своя база документов / vector DB — бонусная фича, только после всего остального.

## 2. Архитектура и пайплайн

```
[Upload docx/pdf/txt]
      │
      ▼
[Text extraction]  python-docx / pypdf
      │
      ▼
[Chunking]  sliding window: 3–5 предложений, overlap 1 предложение
      │
      ▼
[Query generation]  10–20 фраз по 5–10 слов (не полностью рандомно — см. 2.2)
      │
      ▼
[Web search]  SerpAPI / ScrapingBee / ddgs → топ-5 URL на фразу
      │
      ▼
[Scraping + cleaning]  trafilatura → основной текст страниц
      │
      ▼
[Stage 1: bi-encoder retrieval]  sentence-transformers, cosine по чанкам
      │
      ▼
[Stage 2: cross-encoder rerank]  перепроверка топ-кандидатов
      │
      ▼
[Classification]  verbatim / paraphrase / original (правила на двух скорах, см. 2.4)
      │
      ▼
[Report]  % схожести, подсветка фрагментов, URL источников, вердикты → PDF
```

### 2.1. Парсинг документов
- `python-docx` для .docx, `pypdf` для .pdf, plain read для .txt.
- Нормализация: unicode-нормализация (NFKC), схлопывание пробелов, удаление колонтитулов у PDF (эвристика: строки, повторяющиеся на каждой странице).

### 2.2. Генерация поисковых фраз — первое улучшение против исходного ТЗ
Исходное ТЗ говорит «random phrases». Случайность — плохая стратегия. Вместо неё:
- Разбить текст на предложения (spaCy `en_core_web_sm` sentencizer или `nltk.sent_tokenize`).
- Выбрать фразы с наибольшей «отличительностью»: окно 5–10 слов с максимальной суммой IDF (IDF-таблица считается на самом документе или берётся из предобученного TF-IDF на любом корпусе). Редкие обороты находят плагиат лучше случайных.
- Количество: ~1 фраза на 100 слов документа, минимум 10, максимум 30 (лимит расхода поискового API).

### 2.3. Скрапинг
- Поиск: **`ddgs`** (DuckDuckGo Search) — основной способ. Бесплатная Python-библиотека, **без API-ключа и оплаты**, работает из РФ без ограничений. `pip install ddgs`. Достаточно для 10–30 запросов на документ + кэш.
- **Fallback: SearXNG** — если ddgs начнёт капчевать/ограничивать при частых запросах. Бесплатный self-hosted метапоиск (агрегирует DuckDuckGo, Bing, Brave и др.), поднимается локально в Docker, полностью под вашим контролем, бесплатно и работает из РФ:
  ```bash
  docker run -d -p 8080:8080 --name searxng searxng/searxng
  ```
  Далее запросы к вашему инстансу: `GET http://localhost:8080/search?q=...&format=json`. В коде сделайте переключатель: сначала ddgs, при ошибке/капче — SearXNG (флаг в конфиге `search_backend: ddgs|searxng`).
- Извлечение основного текста: **trafilatura** (лучше BeautifulSoup «в лоб»: сам убирает меню, футеры, рекламу).
- Кэширование результатов (sqlite/файловый кэш) — иначе отладка будет повторно дёргать поиск и страницы.
- Таймауты, ретраи, user-agent, обработка 403/капч: страница не скачалась → пропускаем, фиксируем в отчёте как «недоступный источник».

### 2.4. ML-ядро сравнения

**Модели (фиксируем для воспроизводимости):**
- Би-энкодер: `sentence-transformers/all-MiniLM-L6-v2` (быстрый, CPU-friendly). В ablation дополнительно: `intfloat/e5-base-v2` — по опубликованным результатам на задаче детекции плагиата E5 заметно сильнее MiniLM.
- Кросс-энкодер: `cross-encoder/ms-marco-MiniLM-L-6-v2` или `cross-encoder/stsb-roberta-base`.
- Бейзлайн: `sklearn.TfidfVectorizer(ngram_range=(1,2), max_features=5000)` + cosine.

**Классификация фрагмента (прозрачные правила поверх двух скоров):**
- lexical = косинусное сходство TF-IDF (или доля общих n-грамм, n=5);
- semantic = скор кросс-энкодера (после sigmoid → [0,1]);
- `verbatim`: lexical ≥ T1 **и** semantic ≥ T2;
- `paraphrase`: lexical < T1 **и** semantic ≥ T2;
- `original`: semantic < T2.
- Пороги T1, T2 **не подбираются на глаз** — калибруются по валидационной части PAWS (максимизация F1), это отдельный шаг пайплайна и строчка в README.

**Агрегация в итоговый процент:** доля чанков документа с вердиктом verbatim (вес 1.0) + paraphrase (вес 0.5), нормированная. Формула фиксируется в README.

## 4. Evaluation layer (обязательный, отличает проект от поделок)

### 4.1. Данные
- **PAWS** (Paraphrase Adversaries from Word Scrambling) — пары «предложение / перефраз или нет», ~65k пар. Основной бенчмарк.
- **STS-B** (test split) — регрессионная оценка семантического сходства (Spearman/Pearson корреляция скора модели с gold score).
- Свой мини-корпус: 10–15 текстов (свои + статьи), для части вручную сделать перефраз (в т.ч. прогнать 2–3 через LLM с промптом «перепиши своими словами») — это проверка фичи детекции LLM-рерайта. Разметить руками, положить в `data/eval/`.

### 4.2. Метрики
- На PAWS: Accuracy, Precision, Recall, F1, ROC-AUC для бинарной задачи «перефраз vs не перефраз».
- На STS-B: Spearman-корреляция.
- На своём корпусе: confusion matrix по трём классам (verbatim/paraphrase/original) — считается вручную по разметке, это нормально при n≈100–200 фрагментов.
- Латентность: среднее и p95 время сравнения «один фрагмент ↔ один источник» на CPU — записать в README (cost-awareness — сигнал 2026 года).

### 4.3. Ablation (обязательная таблица в README)
Минимум 4 строки, одинаковый eval-набор:

| Подход | Precision | Recall | F1 | ROC-AUC | Latency/пара |
|---|---|---|---|---|---|
| TF-IDF + cosine (baseline) | | | | | |
| Bi-encoder (MiniLM) + cosine | | | | | |
| Bi-encoder (E5-base) + cosine | | | | | |
| Bi-encoder → Cross-encoder rerank (полный пайплайн) | | | | | |

Ожидаемая история (её и рассказываете на собеседовании): TF-IDF хорош на копипасте и проваливается на перефразе; би-энкодер поднимает recall; кросс-энкодер добирает precision. Если получилось иначе — это тоже результат, разбираете в failure analysis.

### 4.4. Failure analysis (обязательный раздел README: «Where this breaks and why»)
Минимум 5 кейсов. Типичные кандидаты:
- общепринятые формулировки/цитаты (законы, определения) → ложные verbatim;
- очень короткие чанки → нестабильный семантический скор;
- страницы с пейволлом/JS → пустой скрапинг → пропущенный источник;
- перефраз с заменой чисел/имён;
- многоязычный текст.
Для каждого: пример, причина, что бы вы сделали с бОльшим бюджетом времени.
